# IntervalAgent V2 rebuild: functional and non-functional requirements

Status: accepted baseline for phased implementation, October 23, 2026. Phase 1 originally had a separately authorized $2 API ceiling; Akshay subsequently explicitly removed that ceiling for local testing. Usage accounting and per-run/workspace limits remain. Requirements describe the complete five-phase target; they are not all implemented. UI/manual acceptance belongs to Akshay. See [STATUS.md](STATUS.md).
Read [PLAN.md](PLAN.md) for five phases with three-line briefs. The original root `SPEC.md` continues to describe V1.

## Product and architecture contract

Use six synthetic scenario families for each of two businesses: twelve selectable client instances with different facts/policies. No spreadsheet import is required. A tester plays customer, sandbox operator or business contact within a private workspace; each has distinct permissions. Project-maintainer rights are separate. Scenarios initialize coherent facts, not dialogue scripts.

Phase 2B delivery: Northside Fitness and Cedar Home Services each provide six cases. Scenario labels are presentation metadata; dated source notes, payments and recognition policy are supplied as facts to the unchanged four-agent runtime. Cedar requires operator review for recognition; the current checkpoint can gather evidence and save supported non-financial updates but has no operator payment-approval action. Do not present that missing action as a completed financial workflow. Operator corrections, the second source mapping, new simulated payment operations and evaluated improvement remain later checkpoints.

Four roles: Customer / Case Orchestrator, Business Verification, Account Resolution, Reviewer. Customer owns conversation/simple scoped reads. Business Verification owns a separate business dialogue/pending request. Account Resolution interprets commitments/requests, reconciles evidence and proposes typed updates/options. Reviewer checks proposals and communications. Guarded tools perform reviewed writes; no arbitrary SQL. Raw transcript logging needs no model. Names, lookups or row insertion alone do not justify a role.

Use the OpenAI Agents SDK for TypeScript with specialists as tools; application code enforces authorization and executes operations. A responsibility handoff need not transfer the customer-facing conversation. Pending business work is persisted and the active run ends; a linked reply resumes the responsible work and returns evidence to the orchestrator. An evaluation harness is software, not a fifth runtime agent. Reviewer may also propose improvements outside a customer turn.

The factory combines reusable roles, versioned business configuration, scoped tools, a source adapter and evaluated feedback. Each source needs a typed schema/capability mapping. Credentials, source-specific queries and unknown-schema interpretation do not belong in agent prompts. Keep source data separate from application conversation/run/feedback storage.

| FR-22 | Persist isolated restricted tester workspaces. | Starting defaults: fixed 24-hour lifetime, 10 accepted customer turns/case. Phase 2B workspace upgrade: add only missing seeded cases under the existing row lock, after authorization and expiry checks. Derive their snapshot/opening dates from the original fixed workspace lifetime. Do not replace saved cases, update their policies, erase histories, consume admissions/turns/model calls, reset counters or extend expiry. The business-filtered dashboard reads the same committed case records as operator oversight; it does not infer received money from a promise or report contact execution from a planned event.

Define the reads and narrow case-update/planned-event commands needed in Phase 1, plus the explicitly authorized recognition of existing business-confirmed synthetic payments. New-payment and arrangement commands remain Phase 3. Separate permissions and validate every write. Unsupported external source writes remain disabled. No generic plugin, arbitrary SQL or spreadsheet endpoint is required.

Simulated writes belong to the application's ledger. Subsequent tool reads reconcile source snapshots and committed local operations without double counting, preserving provenance for each. Recording a previously received payment is a recognition operation, not a new payment attempt; match the account/invoice and check the snapshot's coverage before applying any amount. A source adapter swap cannot silently erase local effects or claim an external database was changed.

## Non-functional requirements

| ID | Requirement | Acceptance evidence |
| --- | --- | --- |
| NFR-01 | Isolate development and preserve production V1. | Work stays local on `v2-rebuild` until explicit push authorization. Development needs no main merge/deploy/config change, production credentials or production DB writes. Paid/public behavior cannot activate silently. |
| NFR-02 | Validate inputs, model outputs, tools, workspace/business/case scope and actor authority. | Reject foreign IDs/forged roles. Public sandbox roles cannot grant maintainer rights or other testers data. Connections are maintainer configuration; untrusted text cannot select URLs, SQL, credentials or policies. |
| NFR-03 | Preserve financial/evidence integrity. | Use integer cents and validated date/policy semantics; recheck versions before writes. Transactions commit effects/audit together. Accepted case updates and their saved confirmations commit together; financial success claims require a durable operation receipt. Rejected/stale writes cannot produce success messages. Unknown/unavailable is not fabricated as empty, zero or verified. |
| NFR-04 | Bound nested work and demo admission; follow the approved spending policy. | Keep server-side request/token/iteration/deadline, turn, business-reply, eval and workspace/reset limits. Local testing has no aggregate dollar ceiling following Akshay's explicit removal; retain atomic pre-call reservations and conservative unknown-usage accounting. Reset cannot erase usage or replenish abuse limits. Provider billing/quota is independent. STOP/history reads remain available at the turn cap without model calls while the workspace is valid. |
| NFR-05 | Handle duplicates, concurrency, cancellation and interruption. | Stable operation/message keys prevent repeated effects/publication; stale decisions fail; timeout does not imply failure. STOP suppresses outreach; takeover fences automatic publication. Recovery reads committed state/receipts before retrying. Test interruption before commit and after commit/before response, plus reset during an active run. |
| NFR-06 | Maintain understandable code and a narrow adapter boundary. | Review connected call paths/contracts. Source mapping changes require no agent edits; policy is not copied across unrelated modules. Prefer the SDK over a new orchestration framework. |
| NFR-07 | Separate runtime, tuning and evaluation expectations. | Hidden/final holdout answers are absent from agent context and tool records. Declare comparison cases/criteria/versions/budgets; retain failed candidates. Do not repeatedly tune to final test results. |
| NFR-08 | Protect credentials, evidence and diagnostics. | No secrets/connection URLs in prompts, browser payloads or artifacts. Allowlist visible fields, deny cross-business access, and use bounded summaries rather than private chain-of-thought. |
| NFR-09 | Provide usable, accessible operator/business/client flows. | Akshay can select, chat, inspect evidence, correct, review and confirm with keyboard controls and readable narrow layouts. Show waiting/failure truthfully; browser acceptance remains his unless delegated. |
| NFR-10 | Measure quality and responsiveness honestly. | Record run/role/tool latency, calls and usage for declared samples. Avoid unnecessary roles/model polling; show pending state promptly. No unmeasured production SLA or real collection-lift claim. |
| NFR-11 | Make verification reproducible and proportionate. | Offline tests/replay need no key; DB tests use an isolated dedicated test database. Live samples have approved bounds and pinned artifacts. Run applicable checks and two labeled self-review/fix passes; distinguish API/browser/independent review evidence. |
| NFR-12 | Persist bounded cross-party work without scheduling or unsafe resumption. | End active runs while waiting; resume on authorized replies/actions within host limits. Evaluate expiry/overdue on activity; no timed reminders, polling or automatic future execution. Waiting pauses contested demands but cannot clear STOP/takeover. Late replies cannot revive expired workspaces. |
| NFR-13 | Enforce limited persistence and free-tier-compatible operation. | Check fixed 24-hour expiry before access/writes using real server time, independent of the scenario clock. Scenario changes cannot extend expiry or reset budgets. Scoped cleanup is bounded on activity/manual maintenance; shared artifacts survive expiry. Store state in PostgreSQL, not function memory/disk. Later hosting must fit verified Vercel/Neon quotas with separate V2 configuration; $0 infrastructure is quota-dependent and excludes model calls. |

## Coverage and learning boundaries

Across both businesses, starting situations cover payment after the snapshot, partial/unallocated payment, conflicting reference, cancellation/renewal overlap, options negotiation/changed affordability and pending/failed operations. Vary policies and records rather than merely names. Follow-up may redirect any case.

Cross-cutting checks cover stale synthetic data, incomplete business replies, wrong invoice, partial/pending payment, unauthorized responders, no-response/late/duplicate work, promise-versus-receipt and request-versus-approval state, ambiguous dates, preference changes, STOP at the turn cap, expiry/reset isolation, stale proposals and unsafe lessons. They are not prescribed transcripts; real-model success is empirical.

## Cross-party evidence and handoff contract

The required local demo has two communication surfaces: customer chat and a business verification inbox/response form, plus operator oversight. Notifications/messages are simulated in-app; no external email/SMS or real business contact is authorized by this specification.

A verification request records its ID, business/account/invoice/case linkage, claim and source snapshot version, requested facts, status and timestamps. Before a new request, collect the customer's matching invoice number; the displayed case invoice alone is insufficient. A reply records the simulated responder, source message, payment facts and request linkage. Business Verification interprets short replies against the actual question: "yes" can confirm explicitly scoped terms, while a vague request still needs clarification. A clear paid-amount assertion for the linked invoice can become `business_reported` even with unknown date/settlement: quote it as the business's report and offer a dispute here, without another settlement questionnaire. Keep full evidence/unknown fields for resolution and review. A report alone cannot authorize financial recognition; that still requires complete policy-compliant evidence. A later customer dispute pauses automatic replies for operator review; differing amounts alone do not trigger that hold before the customer receives the report. Clarify genuinely unclear account/amount evidence; references remain optional.

Account Resolution receives evidence and uses validation/calculation tools to assess the obligation and proposed next step. Reviewer checks sufficiency, matching and communications. Business confirmation alone does not authorize a financial write. The orchestrator uses current state/reviewed responses; changed claims, new evidence, workspace expiry, STOP and takeover fence obsolete work. Test distinct objectives and access boundaries.

## Case updates, planned events and demo lifetime

Case interpretation proposes structured updates; tools validate scope, allowed fields, amounts/dates, revision, review linkage and authority before writing state/audit and the accepted customer confirmation transactionally. Save raw incoming chat independently. Clear commitments/preferences and extension requests need no extra operator click after review. Financial exceptions/adjustments and uncertain evidence need operator approval. Phase 1 now includes existing-payment recognition under an explicit synthetic business policy: a reviewed Account Resolution proposal must match correlated business evidence. Commit a business-provenance receipt, integer-cent balance reduction, audit and confirmation together. Reject duplicates, overpayments, future dates, dates at/before the balance snapshot and operator-required proposals. Negative/pending evidence cannot support recognition; report that no matching payment was located rather than asserting nonpayment. New simulated charges/arrangements remain Phase 3. No real payment executes.

An extension is automatically approved only under an explicit business policy authorizing that exact change with required customer confirmation. Otherwise it remains requested until an operator decides; the agent cannot invent an approval policy.

For example, "$50 Friday, more time for the rest" records a promise and extension request, not a receipt or approved extension. "Call tomorrow afternoon" records channel/date/window using the displayed case clock and client timezone. Clarify missing details instead of inventing time, address or consent. Changed preferences supersede events; STOP blocks them. Planned events never claim execution or schedule agents, calls, email or reminders. Show if their dates exceed demo expiry.

Interactive case time uses current server time displayed in the client's timezone; initialize synthetic snapshot/payment dates relative to workspace creation. Offline replay may pin a separate scenario clock. Keep effective business dates separate from actual audit timestamps. Workspace expiry, admission and spending use real server time; fixture/replay dates cannot alter access or allowances.

Default private-workspace lifetime is 24 hours from creation; activity does not silently extend it. A valid same-browser session restores histories, business replies, case updates/events, feedback and private lesson versions. Ten accepted customer turns/case is the starting cap; retries do not double-count and STOP/history reads remain available. Set separate reply/eval/admission/reset limits and shared API budgets before live activation. Anonymous cross-device recovery is outside scope; losing the browser session may lose access. New/reset workspaces do not reset global spending protection.

Reject access/late replies after expiry; clean up in bounded batches on activity or explicit maintenance, without a scheduler. Show reset/expiry explicitly. Simulated operator/business switching stays inside the tester workspace. Only the maintainer can publish shared profiles/lessons; V1 evidence, fixtures and curated artifacts are separate from expiring demo data.

Application learning changes evaluated instructions, lessons and delegation/clarification/review behavior. V1's outreach picker is a separate learned strategy. Neither implies changing OpenAI model weights. A corrected account fact does not automatically justify an agent lesson. Shared lessons need explicit scope and cross-business regression evidence.

The final report separates deterministic checks, model behavior, simulated operations, human assessment and unmeasured real-world effectiveness. Positive improvement is not guaranteed; rejection and rollback are valid demonstrated outcomes.

## Deferred scope and review decisions

No spreadsheet import/export, real messages/payments, timed execution/reminders, universal schema detection, connector marketplace, arbitrary industry coverage, automatic lesson promotion, model-weight training, cloud fleet or public launch is required. A real connector needs a separately reviewed schema/authentication/freshness/capability mapping.

Akshay reviews exact business/client profiles, payment-policy thresholds, operator/business-contact permissions, source mapping, verification/manual-follow-up rules and API/model limits before implementation. Automatic reviewed case updates, the business inbox and planned-event recording are agreed. No spreadsheet feature is required. The 24-hour/10-turn defaults and other abuse/admission limits remain reviewable. Fresh-record injection, receipt upload/OCR, external delivery and real payment-provider integration remain optional separate decisions.

## Hosting target

Optional future target: Vercel Hobby for the personal non-commercial Next.js demo and Neon Free for persistent PostgreSQL. Free quotas are finite and can be shared across account projects; cold starts and exhausted quotas need explicit handling. No dedicated worker or scheduling provider is needed: bounded active requests persist state and end while awaiting a party. Preserve state for explicit request-driven continuation if a run cannot finish within host limits. API spending remains separate and bounded.

This is hosting readiness, not permission to deploy. Any later deployment requires separate authorization, verified account availability and isolated V2 credentials/database/configuration. Production V1 stays frozen. Check the current [Vercel plan](https://vercel.com/docs/plans/hobby), [function limits](https://vercel.com/docs/functions/limitations), [Neon pricing](https://neon.com/pricing) and [scale-to-zero behavior](https://neon.com/docs/introduction/scale-to-zero) before deployment; PLAN.md records the October 23 quota snapshot.
