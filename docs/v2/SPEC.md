## Product and architecture contract

Use six synthetic scenario families for each of two businesses: twelve selectable client instances with different facts/policies. No spreadsheet import is required. A tester plays customer, sandbox operator or business contact within a private workspace; each has distinct permissions. Project-maintainer rights are separate. Scenarios initialize coherent facts, not dialogue scripts.

Phase 2B delivery: Northside Fitness and Cedar Home Services each provide six cases. Scenario labels are presentation metadata; dated source notes, payments and recognition policy are supplied as facts to the unchanged four-agent runtime. Cedar requires operator review for recognition; the current checkpoint can gather evidence and save supported non-financial updates but has no operator payment-approval action. Do not present that missing action as a completed financial workflow. The source mapping is covered in Phase 2D below; new simulated payment operations and evaluated improvement remain later checkpoints.

Phase 2C delivery: case-specific operator corrections now capture the latest reviewed attempt, affected role, feedback, original result and revision. Saving is a no-model-call pause. An explicit retry/resume supplies that feedback to the existing model-led workflow and required Reviewer, preserving original/revised history and appending only a reviewed accepted reply. Feedback cannot provide business evidence, approve policy exceptions, recognize/replay payments or reverse committed effects. Supported non-financial updates still require real customer-message sources and existing validation. Reusable lessons are not activated by this action; those remain Phase 4. The source mapping is covered in Phase 2D below; financial operations remain pending.

Phase 2D delivery: fixture and PostgreSQL adapters now share a validated account-source contract and investigation entry point. The PostgreSQL mapping reads differently shaped synthetic organization/account/payment tables in the isolated test database. Both carry `synthetic` provenance plus a separate adapter identifier, scope, version, timestamp and evidence references. Strict validation rejects invalid money, unknown policy/payment states, malformed or future-dated snapshots, mismatched scope/invoice and unavailable mappings before model calls; there is no fixture fallback. Shared checks and scripted SDK journeys prove normalized inputs and unchanged role definitions, not live model quality. The application continues using its saved synthetic records; no source-selection UI or production connector is included.

A source replacement that differs from locally committed payment evidence fails with `reconciliation_required`, preserving saved effects. Automatic reconciliation of changed external snapshots is not implemented. Additional schemas require explicit server-side mapping and a bounded/read-only connection; changing a URL cannot interpret an arbitrary database.

Phase 3A delivery: scoped synthetic payment policy and local today/tomorrow are supplied in run context. The orchestrator can answer simple options directly or choose Account Resolution to calculate a concrete full-balance proposal. Avoid re-reading supplied policy/dates; specialist date tools remain for other offsets, and an explicit policy recheck is available to the orchestrator. The latter uses a code tool for integer-cent splitting and monthly calendar dates. Reviewer checks the offer; commit validation independently recalculates the exact terms. Save a strict `payment_proposed` case update with customer source ID, policy/source versions, invoice, balance and schedule, atomically with reply/audit. Offers never authorize an agreement, promise, payment or balance reduction. Phase 3A itself added no agreement/payment action; the Phase 3B contract below adds those controls separately. Earlier receipts/recognition remain a distinct evidence workflow; recognition and an offer cannot share one result.

Versioned synthetic policies: Northside supports card, bank transfer or cash in 1/2/3 payments starting within 30 local days; Cedar supports card or bank transfer in 1/2/3/4/6 payments starting within 45 local days. Both cover the full remaining balance with zero added fees/interest. Counts must produce positive whole-cent installments; last payments receive remainder cents. Monthly dates preserve the first day-of-month anchor with month-end clamping, including leap years. Missing method/count/date needs clarification. Out-of-policy terms require alternatives or operator review, not invented authorization. Unknown businesses have no fallback policy.

Runtime displays one row per model call, updating started to completed and showing returned tool-request names. Persist up to forty events within the existing twenty-call bound, retaining the initial dispatch. The total completed-call counter remains authoritative; label missing events in legacy truncated runs instead of inventing history. The expanded list has bounded height and keyboard scrolling.

Proposal persistence is append-only within case updates. Exact retries deduplicate; newer offers supersede prior display. Changed policy/source/invoice/balance/schedule or an elapsed start date makes an offer stale against the supplied case clock and ineligible for a new reviewed write. UI labels use the last saved case time, not a continuously ticking expiry check. Review rejection, stale revision, STOP, takeover, reset and workspace expiry block publication. Phase 3B below adds explicit consent/execution. Partial-balance offers, custom cadence and financial approval/reconciliation controls remain unavailable. No reusable learning is activated.

Phase 3B delivery: strict `confirm_plan` and `simulate_payment` commands require current case revisions and stable command IDs. Confirmation must exactly match the latest saved reviewed proposal and its audit, with current policy/source/invoice/balance/date validation. Save the agreement and explicit control action; chat acceptance alone cannot confirm or pay. A replacement confirmed plan supersedes the old plan for execution. Payment derives the next installment/amount from the latest agreement, checks the current source/balance against that plan's successful operations, and requires it to be due on actual server-local time. No client-supplied amount, receipt, approval or arbitrary financial write is accepted.

Policy versions are now `northside-options-2` and `cedar-options-2`: plan confirmation is enabled; only card/bank-transfer simulated execution is enabled. Cash remains offerable/confirmable but needs operator receipt approval, not yet implemented. Existing-payment recognition policies remain distinct and unchanged; Cedar's operator-required recognition cannot be bypassed by these new-payment controls. Earlier policy-version offers must be recalculated.

The explicitly labelled demo processor returns the tester-selected succeeded/failed/pending/unknown state without a network call or real payment credentials. Persist a scoped operation with consent linkage, installment, invoice, amount, selected outcome, time, before/after balance/version and optional receipt ID. Only succeeded appends a `simulated_operation` receipt and reduces the balance in the same transaction. Failed permits a new explicit attempt; pending/unknown blocks subsequent attempts/confirmations until operator reconciliation. Existing pending records or unresolved business verification also block new payments. Never infer a settlement from a timeout or missing explanation; the saved operation is authoritative. This is a synthetic ledger proof, not provider integration.

The operation transaction precedes agent explanation. Supply the saved agreement/operation and action trigger to the existing SDK roles; the orchestrator chooses useful Account Resolution assessment, and Reviewer checks the communication. Neither chat, feedback, Reviewer approval nor an explanation retry can execute/replay an operation or approve a financial exception. Assessment cannot propose recognition or another payment offer. Model failure/review rejection leaves the committed effect visible and unchanged; retry only the explanation using saved evidence. Preserve action/receipt/audit linkage. STOP, takeover, stale revisions, reset and expiry fence new actions/late replies without reversing an existing effect.

Private JSONB fields preserve legacy cases without migration/reset. Bound six plan confirmations and twelve attempts per case within existing action/usage/lifetime limits; these controls do not use chat-turn allowance. Read responses add an observation timestamp for actionable due-date UI; refresh after dates change, and always recheck real time on the server. Confirmation may record future schedules but never schedules an agent or extends workspace expiry. Generic Resume cannot approve, settle or reverse a payment. The Phase 3C and closeout contracts below add separate financial decisions and compensating operations.

Phase 3C delivery: takeover-only `approve_recognition` targets this case's latest accepted review with complete correlated business confirmation. Retain the configured recognition policy; explicit operator authority replaces only the automatic-policy gate. Reuse customer invoice, linked/latest business reply, date, duplicate and balance checks. New unreviewed messages invalidate the approval. Receipt provenance is `operator_decision`, linked to the decision and original business request/reply. This does not initiate a new payment or allow arbitrary amount/date/receipt overrides.

`reconcile_payment` targets one unresolved pending/unknown simulated operation, its confirmed installment and unchanged source/balance. The operator explicitly records settled or not-settled using synthetic evidence; no external processor is queried. Append the decision without rewriting the original operation. Settlement atomically saves one operator-provenance receipt and balance/version change; not-settled saves no money. Effective operation state drives the plan/hold guards, while original state and the decision remain separately inspectable. Successful reconciliation advances only that installment; a future installment remains blocked. Not-settled requires a new explicit attempt rather than automatically retrying.

Both strict commands bind case revision/target/stable ID and require a trimmed 10–1200 character note plus 1–80 character evidence reference, with no client amount/receipt fields. Apply existing workspace/case/STOP/run/reset/expiry guards and at most twelve financial decisions within sixty actions. Save before any model explanation; retain takeover, current runtime, messages and chat-turn count. Explicit resume/retry supplies original/effective operations and decisions to the same four roles with required Reviewer and no execution tools. Rejected, failed or repeated explanation cannot undo/replay the effect. This is workspace-local synthetic operator authority, not production authentication or verified bank evidence.

Phase 3 closeout: the same decision boundary supports `approve_credit` (bounded positive cents, latest accepted review/current source and messages, once per review), `approve_extension` (latest undecided saved request, nonpast date), `reverse_receipt` (one unreversed local settled receipt only), and `reconcile_record` (one unresolved imported pending payment, settled/not-settled). Credits lower debt without receipts; reversals retain/annotate the receipt and restore its amount, without issuing a refund. Source reconciliation retains/annotates the pending record and creates a distinct operator receipt only if settled. Preserve evidence and before/after balances/source versions. Refuse duplicate/over-balance/stale effects and unresolved incompatible operations. Balance corrections make old plans stale, even after a formerly fully-paid plan. An extension does not reschedule installments. No generic policy override editor, changed-snapshot merge, arbitrary external write or real payment/refund is included.

Phase 4 delivery: strict learning commands propose from saved role feedback/current rejected review, compare, activate, reject and roll back. Reviewer diagnosis has no execution tools or evaluation answers. It emits at most one short reusable instruction with a supported focus (invoice clarity, contact preference, verification handoff or payment truthfulness) and role; data/tool repairs and unsupported/authority-bypassing suggestions stay rejected. The comparison harness is software, not a fifth runtime agent. Run matching independent baseline/candidate cases: two targets, regression and safety, preserving outputs, model/call counts, provenance, suite/base/instruction versions and explicit criteria. Recompute eligibility server-side; every candidate row must pass, with a correctness gain or lower calls. Incomplete runs and ties fail. Scripted checks test mechanics but cannot activate a lesson.

Activation requires current suite/model/base, live eligible comparison, unchanged baseline, safe instruction and explicit operator assessment. Scope is private workspace + business + role, optionally scenario family; a scenario lesson overrides its business-wide counterpart. Inject only matching role instructions, subordinate to permissions/evidence/code guards, into subsequent jobs; pin IDs in audit and preserve in-flight versions. Rollback restores a valid prior version or base and appends the actual decision. Retain rejected candidates and earlier suite reports. Reset interrupts pending learning while retaining private curated learning/history/calls; fixed expiry and workspace isolation remain. No shared promotion, weight training, automatic code rewriting or real collection-lift claim. Limits: 8 candidates, 40 learning actions (rollback remains available after exhaustion), 64 reserved calls per workspace; comparison max 32 calls/90 seconds, ordinary conversation limits unchanged. API requests cannot submit instructions/evaluation verdicts or extend authority.

Phase 5A delivery: `eval:v2:replay` validates one checked-in, checksum/version-pinned synthetic live-output archive without model/database clients or fallback. Retain both complete suite-2 role comparisons and their failed cases, one rejected unsafe suggestion, instructions, outputs, tools, usage/latency and provenance/configuration references; do not publish workspace access tokens or credentials. Reuse the existing deterministic scorer unchanged, recompute eligibility and compare with archived verdicts. Gate integrity/reproducibility separately from candidate quality. Unknown usage, metric denominators and uncaptured customer/ledger outcomes remain explicit. Produce Markdown/JSON reports; reject malformed/oversized/missing/tampered/incompatible evidence, incomplete cases, duplicate/call-count mismatches and live flags. This is selected saved-output rescoring with reconstructed scoring context, not raw SDK/provider-request replay, new model-quality verification, final holdout or a receipt/collection-lift measure. V1's pinned replay remains intact. Remaining Phase 5 work is not implied complete.

Four roles: Customer / Case Orchestrator, Business Verification, Account Resolution, Reviewer. Customer owns conversation/simple scoped reads. Business Verification owns a separate business dialogue/pending request. Account Resolution interprets commitments/requests, reconciles evidence and proposes typed updates/options. Reviewer checks proposals and communications. Guarded tools perform reviewed writes; no arbitrary SQL. Raw transcript logging needs no model. Names, lookups or row insertion alone do not justify a role.

Use the OpenAI Agents SDK for TypeScript with specialists as tools; application code enforces authorization and executes operations. A responsibility handoff need not transfer the customer-facing conversation. Pending business work is persisted and the active run ends; a linked reply resumes the responsible work and returns evidence to the orchestrator. An evaluation harness is software, not a fifth runtime agent. Reviewer may also propose improvements outside a customer turn.

The factory combines reusable roles, versioned business configuration, scoped tools, a source adapter and evaluated feedback. Each source needs a typed schema/capability mapping. Credentials, source-specific queries and unknown-schema interpretation do not belong in agent prompts. Keep source data separate from application conversation/run/feedback storage.

## Coverage and learning boundaries

Across both businesses, starting situations cover payment after the snapshot, partial/unallocated payment, conflicting reference, cancellation/renewal overlap, options negotiation/changed affordability and pending/failed operations. Vary policies and records rather than merely names. Follow-up may redirect any case.

Cross-cutting checks cover stale synthetic data, incomplete business replies, wrong invoice, partial/pending payment, unauthorized responders, no-response/late/duplicate work, promise-versus-receipt and request-versus-approval state, ambiguous dates, preference changes, STOP at the turn cap, expiry/reset isolation, stale proposals and unsafe lessons. They are not prescribed transcripts; real-model success is empirical.

## Cross-party evidence and handoff contract

The required local demo has two communication surfaces: customer chat and a business verification inbox/response form, plus operator oversight. Notifications/messages are simulated in-app; no external email/SMS or real business contact is authorized by this specification.

A verification request records its ID, business/account/invoice/case linkage, claim and source snapshot version, requested facts, status and timestamps. Before a new request, collect the customer's matching invoice number; the displayed case invoice alone is insufficient. A reply records the simulated responder, source message, payment facts and request linkage. Business Verification interprets short replies against the actual question: "yes" can confirm explicitly scoped terms, while a vague request still needs clarification. A clear paid-amount assertion for the linked invoice can become `business_reported` even with unknown date/settlement: quote it as the business's report and offer a dispute here, without another settlement questionnaire. Keep full evidence/unknown fields for resolution and review. A report alone cannot authorize financial recognition; that still requires complete policy-compliant evidence. A later customer dispute pauses automatic replies for operator review; differing amounts alone do not trigger that hold before the customer receives the report. Clarify genuinely unclear account/amount evidence; references remain optional.

Account Resolution receives evidence and uses validation/calculation tools to assess the obligation and proposed next step. Reviewer checks sufficiency, matching and communications. Business confirmation alone does not authorize a financial write. The orchestrator uses current state/reviewed responses; changed claims, new evidence, workspace expiry, STOP and takeover fence obsolete work. Test distinct objectives and access boundaries.

## Case updates, planned events and demo lifetime

Case interpretation proposes structured updates; tools validate scope, allowed fields, amounts/dates, revision, review linkage and authority before writing state/audit and the accepted customer confirmation transactionally. Save raw incoming chat independently. Clear commitments/preferences and extension requests need no extra operator click after review. Financial exceptions/adjustments and uncertain evidence need operator approval. Phase 1 now includes existing-payment recognition under an explicit synthetic business policy: a reviewed Account Resolution proposal must match correlated business evidence. Commit a business-provenance receipt, integer-cent balance reduction, audit and confirmation together. Reject duplicates, overpayments, future dates, dates at/before the balance snapshot and operator-required proposals. Negative/pending evidence cannot support recognition; report that no matching payment was located rather than asserting nonpayment. New simulated charges/arrangements remain Phase 3. No real payment executes.

An extension is automatically approved only under an explicit business policy authorizing that exact change with required customer confirmation. Otherwise it remains requested until an operator decides; the agent cannot invent an approval policy.

For example, "$50 Friday, more time for the rest" records a promise and extension request, not a receipt or approved extension. "Call tomorrow afternoon" records channel/date/window using the displayed case clock and client timezone. Clarify missing details instead of inventing time, address or consent. Changed preferences supersede events; STOP blocks them. Planned events never claim execution or schedule agents, calls, email or reminders. Show if their dates exceed demo expiry.

Interactive case time uses current server time displayed in the client's timezone; initialize synthetic snapshot/payment dates relative to workspace creation. Offline replay may pin a separate scenario clock. Keep effective business dates separate from actual audit timestamps. Workspace expiry, admission and spending use real server time; fixture/replay dates cannot alter access or allowances.

Default private-workspace lifetime is 24 hours from creation; activity does not silently extend it. A valid same-browser session restores histories, business replies, case updates/events, feedback and private lesson versions. Ten accepted customer turns/case is the starting cap; retries do not double-count and STOP/history reads remain available. Set separate reply/eval/admission/reset limits and shared API budgets before live activation. Anonymous cross-device recovery is outside scope; losing the browser session may lose access. New/reset workspaces do not reset global spending protection.

Reject access/late replies after expiry; clean up in bounded batches on activity or explicit maintenance, without a scheduler. Show reset/expiry explicitly. Simulated operator/business switching stays inside the tester workspace. Only the maintainer can publish shared profiles/lessons; V1 evidence, fixtures and curated artifacts are separate from expiring demo data.

Application learning changes evaluated instructions, lessons and delegation/clarification/review behavior. V1's outreach picker is a separate learned strategy. Neither implies changing OpenAI model weights. A corrected account fact does not automatically justify an agent lesson. Shared lessons need explicit scope and cross-business regression evidence.

The final report separates deterministic checks, model behavior, simulated operations, human assessment and unmeasured real-world effectiveness. Positive improvement is not guaranteed; rejection and rollback are valid demonstrated outcomes.

## Deferred scope and review decisions

No spreadsheet import/export, real messages/payments, timed execution/reminders, universal schema detection, connector marketplace, arbitrary industry coverage, automatic lesson promotion, model-weight training, cloud fleet or public launch is required. A real connector needs a separately reviewed schema/authentication/freshness/capability mapping.
