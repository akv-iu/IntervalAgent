# V2 billing evaluation fixtures

Set: `billing-20261019-1`, authored October 19, 2026. This is synthetic test data, not real business/customer data or measured agent performance.

The set has 36 manually specified cases: 12 development, 12 validation, and 12 final holdout. Each split covers exact payments, ambiguous matches, cancellations, partial payments, missing records, contradictory records, duplicate requests, and tool failures. Family IDs identify distinct relationships/decision conditions; families never cross splits. The same broad category intentionally appears in every split.

`inputs/` contains only customer text, scope, and connected records. Feed records to the scoped read tools; feed only the relevant customer text and tool results to agents. Do not serialize the whole fixture set, manifest, split labels, family IDs, control flags or oracle into a prompt.

`oracles/` contains separately authored expected actions, balances, required evidence and rationale. These values were written explicitly rather than generated by `previewProposal`. They are evaluator-only. The author of this initial set is Codex, which also implemented the application; these are separate case definitions, not independently authored external evidence. Family separation was manually reviewed, and exact input copies are checked by hashes; semantic similarity is not automatically proven absent.

The manifest stores hashes of every input/oracle plus evaluator-only controls. The harness pins the manifest hash. `npm run fixtures:v2:check` checks coverage, public input schemas, all file hashes, and development/validation oracle schemas. It does not score agents, validate holdout outcomes against application behavior, or decode holdout answers. A future final-evaluation runner must explicitly opt in to `loadExpectation(id, { allowHoldout: true })` after prompts and lessons are frozen.

Routine checks may validate holdout public records and hash raw oracle bytes. They never use holdout expected values to choose a prompt/lesson or report a model score. If final outcomes are inspected for tuning, retire this holdout and publish a new version before claiming a fresh final evaluation. Frozen files must not be silently rewritten; a deliberate new set requires new hashes and an explicit pin change.

Fault controls stay inside the evaluator: unavailable or malformed services go through the real tools' sanitized failure behavior. `repeatSubmission` is a future runner instruction to repeat the same customer request with one idempotency key; the persistent runtime is not implemented yet, so this phase does not claim the duplicate-submission end-to-end check passes.

`scripts/v2-eval/` is the only fixture-loading harness. Source import checks keep it outside `src/`, and Next.js tracing excludes this entire fixture tree and the harness from web deployment. Local evaluators can read the repository files; isolation here is an import/tool/deployment boundary, not an operating-system sandbox. No arbitrary filesystem tool is exposed to runtime agents.
